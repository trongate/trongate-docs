validation_errors()

function validation_errors(string|int|null $first_arg = null, ?string $closing_html = null, ?string $scope = null): ?string

Quick Start: Use validation_errors() for general form errors, validation_errors('FORM-login') for errors belonging to one named form, validation_errors('fieldname') for inline errors, or validation_errors(422) for JSON API responses.

Description

Displays validation error messages stored in the session. This flexible function supports four output modes: general error display, scoped error display for a named form, inline field-specific errors, and JSON error responses for APIs.

Parameters

Parameter Type Description
$first_arg string|int|null (optional) This overloaded argument determines the function's mode:
  • If string starting with FORM-: The name of a form for scoped error reporting (e.g. validation_errors('FORM-login')). (Mode 4)
  • If string (no $closing_html): The name of a specific field for inline error reporting. (Mode 2)
  • If int (400-499): An HTTP status code to trigger a JSON error response. (Mode 3)
  • If string (with $closing_html): The opening HTML tag for custom error wrappers. (Mode 1 - Custom)
  • If null: Default general error reporting for all fields. (Mode 1 - Default)
$closing_html ?string (optional) The closing HTML tag when $first_arg is used as an opening HTML tag. Defaults to null. Unused in the FORM- prefix spelling — see Mode 4.
$scope ?string (optional) A form name for scoped error rendering with custom wrappers. Only used in standard mode: validation_errors('</p>', '<p>', 'login'). Defaults to null.

Return Value

Type Description
string|null Formatted validation errors as HTML or JSON (for API mode), or null if no errors exist.

Session Management: Errors are automatically cleared from the session after display. Each error set displays only once per request. A scoped call that abstains (name mismatch) does not clear the bucket — the correct form's block must still be able to render it.

Mode 1: General Error Display (All Errors)

Display all validation errors at once, typically at the top of a form. By default, errors are wrapped in <p style="color: red;"> tags unless ERROR_OPEN and ERROR_CLOSE constants are defined globally.

[code=vf] <h1>Registration Form</h1> <?= validation_errors() ?> [/code]
Example Output

The Email field is required.

The Password must be at least 8 characters long.

Custom HTML Wrappers (Mode 1 Custom)

You can override the default wrappers by passing custom HTML tags:

[code=vf] <?php // Wrap each error individually echo validation_errors('<div class="alert alert-danger">', '</div>'); ?> [/code]

Mode 2: Inline Field Errors (Field-Specific)

Display errors next to specific form fields by passing the field name (string) as the first argument. Errors are automatically wrapped in a <div class="validation-error-report"> container.

[code=vf] <?php echo form_open('users/submit'); echo form_label('Username'); echo validation_errors('username'); // Shows username errors only echo form_input('username', post('username')); echo form_label('Email'); echo validation_errors('email'); // Shows email errors only echo form_input('email', post('email')); echo form_submit('submit', 'Save'); echo form_close(); ?> [/code]

Mode 3: JSON Error Responses (API)

Return errors as structured JSON for API endpoints by passing an HTTP status code (integer between 400 and 499) as the first argument.

JSON Mode Important: When using JSON mode, the function sends headers, outputs the JSON, and exits execution. No further code runs after validation_errors(422).

[code=php] public function api_create(): void { $this->validation->set_rules('email', 'email address', 'required|valid_email'); $this->validation->set_rules('password', 'password', 'required|min_length[8]'); if ($this->validation->run() === false) { // Returns JSON, sets HTTP 422 status, and exits. validation_errors(422); } // Continue with success logic... } [/code]

JSON Output Format (Example)

[code] [ { "field": "email", "messages": ["The email address field is required."] }, { "field": "password", "messages": ["The password must be at least 8 characters long."] } ] [/code]

Mode 4: Scoped Errors (Form-Specific)

Display errors belonging to one named form only. This is useful on pages with more than one form, where a global summary would mix errors from different forms.

Give the form a name with the form_name attribute of form_open(), then render its errors with the FORM- prefix:

[code=vf] <?php echo form_open('auth/login', ['form_name' => 'login']); // ... login fields ... echo validation_errors('FORM-login'); // login form's errors only ?> [/code]

Scoped rendering uses the default error wrappers. Custom wrappers require the position-3 spelling:

[code=vf] <?php // Scoped with custom wrappers: echo validation_errors('</p>', '<p>', 'login'); ?> [/code]

Position 2 is unused in the prefix spelling: validation_errors('FORM-login', '</p>') silently drops the wrapper — the prefix spelling always uses default wrappers. For custom wrappers plus scoping, use the position-3 $scope spelling above.

Abstain semantics: when the requested name does not match the recorded name (wrong name, or no name recorded at all), the call returns null without clearing the error bucket — the correct form's block still renders.

Constraints: form names are strings only, trimmed, and at most 64 characters. Longer or non-string names are never recorded by run() (and never injected by form_open()).

Footgun: a scoped call on a form that declared no form_name renders nothing, silently. If a page's form does not declare form_name, use the no-argument global spelling.

Reservation: a field literally named FORM-* (uppercase prefix) is no longer reachable via inline validation_errors('FORM-*') — the prefix is reserved for scoped rendering. Lowercase form-* fields are unaffected.

Global Error Styling

Define default error wrappers in your configuration to avoid passing them as arguments every time:

[code=php] // In config/config.php define('ERROR_OPEN', '<div class="error-message">'); define('ERROR_CLOSE', '</div>'); [/code]

Prerequisite: Errors must first be set using Trongate's Validation class. The validation_errors() function only displays errors that have already been stored in the session.

Automatic Field Highlighting

The framework automatically injects JavaScript to highlight fields that have validation errors. To enable this behavior, simply add class="highlight-errors" to your form's opening tag:

[code=vf] <?php echo form_open('users/register', ['class' => 'highlight-errors']); // Fields with errors will automatically receive the 'form-field-validation-error' class. ?> [/code]

Common Patterns Summary

Use Case Code Mode Result
Simple form errors validation_errors() Mode 1 (Default) All errors in default <p> format
Styled general errors validation_errors('<div class="error">', '</div>') Mode 1 (Custom) Each error wrapped individually
Field-specific error validation_errors('email') Mode 2 Only email field errors, wrapped in validation-error-report
API response validation_errors(422) Mode 3 JSON with 422 status code and script exit
One form's errors (multi-form page) validation_errors('FORM-login') Mode 4 Only the named form's errors, default wrappers
One form's errors, custom wrappers validation_errors('</p>', '<p>', 'login') Mode 4 Only the named form's errors, custom wrappers
